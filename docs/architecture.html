1产品简介与核心特性

mosaic-examples 是一个演示性质的前端项目，用于展示在浏览器中直接运行分析型数据库（DuckDB-WASM）并驱动声明式可视化（Mosaic / vgplot）的能力。 它不是单一应用，而是一个可切换场景的「画廊」——每个场景都是一个独立的分析问题，配有确定性合成数据和对应的可视化表达。

🦆

数据库驱动可视化

数据存储、聚合、筛选全部在 DuckDB-WASM 中完成，vgplot 只向数据库请求像素级所需的聚合结果，避免百万行数据进入 DOM。

🔒

零外部网络请求

验证器拦截所有非本地请求并报错。数据由 SQL 的 range() 与三角函数合成，完全离线可用。

🖼️

透明 PNG 参考图

每个场景都可导出背景透明的 PNG，作为文档、幻灯片或设计稿中的可复用素材。

🔗

Crossfilter 联动

多个视图通过共享 SQL 选择集联动：刷选散点图，直方图实时过滤。状态保存在 Coordinator 层。

🧪

自动化像素级验证

用 Playwright 驱动 Chromium 逐场景截图，再用 pngjs 分析透明像素占比、墨迹量与饱和度，确保渲染结果有效。

📊

十二种分析模板

从密度热图到运营驾驶舱，覆盖常见的大规模数据分析场景。每个场景都是自包含的 SQL + 绘图声明。

2系统总览架构图

系统由浏览器运行时与构建/验证工具链两大部分组成。浏览器端是一个单页应用，根据 URL 参数加载不同场景； 工具链负责 TypeScript 编译、Vite 打包、以及基于 Playwright 的截图验证。

架构解读

浏览器运行时是用户直接交互的部分。入口文件 main.ts 读取 URL 参数中的 scene， 动态组装对应的 SQL 建表语句与 vgplot 声明。场景路由决定执行哪一个 if 分支， 外壳 UI 负责标题、副标题、导航链接和状态条。

vgplot（来自 @uwdata/vgplot）是 Mosaic 框架的声明式绘图 API。 它不直接绘图，而是把绘图需求翻译为数据查询，交给下层的 Coordinator 调度。 Coordinator 负责缓存、合并查询、以及跨视图的 crossfilter 联动状态。

DuckDB-WASM 在单独的 Web Worker 中运行，执行实际的 SQL 计算。 项目同时打包了 MVP（最小可行产品）和 EH（异常处理）两个 WASM bundle，运行时由浏览器能力自动选择。 由于数据全部在 Worker 内合成与查询，主线程只接收聚合结果，因此百万行数据也能流畅交互。

构建与验证层运行在 Node.js 环境中。vite build 打包静态资源， validate.mjs 启动 vite preview 服务器，用 Playwright 驱动 Chromium 逐场景访问， 截图后交给 pngjs 做像素级分析，最终产出 out/ 目录下的透明 PNG 参考图。

3数据生成与渲染流水线

每个场景的运行都遵循相同的五步流水线：初始化引擎、合成数据、构建查询、渲染图表、响应用户交互。 以下架构图以数据流的方式展示了各模块之间的调用顺序。

数据合成
可视化声明
数据库计算
渲染输出

流水线详解

第一步：初始化引擎。调用 duckdb.selectBundle() 在 MVP 与 EH 两个 WASM bundle 中选择当前浏览器支持的版本， 创建 Worker 并实例化 AsyncDuckDB。这一步只在页面首次加载时发生，切换场景不会重建数据库。

第二步：合成数据表。每个场景对应一条 CREATE TABLE ... AS SELECT ... FROM range(N) 语句。 利用 DuckDB 的 range() 表函数生成指定行数（18 万到 52 万不等）的序列，再通过三角函数与模运算组合出确定性的合成数据。 由于数据完全由公式决定，每次运行的结果完全一致，方便做像素级回归测试。

第三步：声明可视化。开发者用 vgplot 的声明式 API 描述图表类型（heatmap、denseLine、hexbin、barY、cell、dot、spike、vector 等）、 坐标轴、颜色方案与交互方式（panZoom、intervalXY、crossfilter）。Coordinator 接收这些声明，将其翻译为对数据库的具体查询， 并启用查询缓存（cache: true）与结果合并（consolidate: true）以减少往返。

第四步：数据库聚合。实际的分箱、计数、平均等运算都在 DuckDB-WASM 中完成。 例如密度图场景中，Mosaic 不会把一百万行点全部发给浏览器渲染，而是请求数据库按像素尺度分箱后返回二维直方图数据， 数据量从百万级降到约屏幕像素数（约十万分之一）。

第五步：渲染与交互。vgplot 将聚合结果渲染为 SVG 或 Canvas 图形。用户进行缩放、刷选等操作时， 交互事件反馈给 Coordinator，Coordinator 修改查询参数后重新执行第三、四、五步，形成闭环。 全局对象 window.__mosaicDemo 暴露 ready、scene、rows、interactions 等状态， 供验证脚本读取。

走查解读

第 1 步：启动验证器。用户运行 npm run render，Node.js 执行 tools/validate.mjs。 脚本首先以子进程方式启动 vite preview，监听 127.0.0.1:41732，轮询直到服务器返回 HTTP 200。

第 2 步：驱动浏览器。Playwright 启动系统安装的 Google Chrome 无头模式， 为每个场景新建一个页面。页面请求被拦截器路由：仅允许 127.0.0.1、blob:、data:， 任何外部域名请求都会被记录为失败并中止——这保证了「纯本地运行」的承诺。

第 3 步：等待就绪。页面加载 index.html，Vite 提供打包后的 main.ts。 主线程创建 DuckDB-WASM Worker，执行 CREATE TABLE points AS SELECT ... 合成一百万行点数据， vgplot 渲染密度热图。全部完成后，window.__mosaicDemo.ready 被置为 true， Playwright 的 waitForFunction 检测到后继续。

第 4 步：截图落盘。在 export=1 模式下，页面外壳隐藏（仅保留图表）， page.screenshot({omitBackground: true}) 生成透明背景的 PNG，写入 out/density-transparent.png。

第 5 步：像素校验。pngjs 读取 PNG 并逐像素分析：透明像素需 > 18%（确保背景透明）、 墨迹像素（alpha > 32）需 > 8000（确保有实质内容）、饱和像素需 > 1200（确保彩色数据可见）。 三项均通过，场景才算渲染成功。

5验证与测试体系

项目的测试不依赖断言库，而是围绕「真实渲染 + 像素分析 + 交互验证」构建了三层保障， 确保每个场景既能正常绘制、又能响应用户操作、且不依赖任何外部资源。

验证体系解读

第一层：静态检查。运行 npm test 时，先执行 tsc --noEmit 做类型检查， 再执行 vite build 确保打包无错。验证器启动时还会读取 catalog.json 并断言场景数 ≥ 12， 防止场景列表意外缩减。

第二层：渲染检查。这是项目最有特色的验证方式——不用 DOM 断言，而是直接分析 PNG 的像素分布。 三项指标各有侧重：透明像素占比确保背景确实是透明的（而不是画了白色矩形）， 墨迹总量确保图表有实质内容（而不是空白或加载失败）， 彩色饱和度确保数据是彩色绘制的（而不是全灰或单色）。

第三层：交互检查。非 --render-only 模式下还会做两件事： 一是用 page.route 拦截所有请求并审计来源，任何非本地请求都算失败； 二是在图表区域模拟鼠标拖拽（按下 → 移动 → 抬起）， 然后断言 window.__mosaicDemo.interactions > 0，确认 pointer 事件确实触发了图表的交互逻辑。 同时全程监控 console.error 和 pageerror，任何报错都计入失败。

场景间的数据共享策略：前三个场景（density / signals / linked）各有独立的表结构（points、signals、events）， 其余九个场景复用同一张 measures 大表，只是选择不同的列与聚合方式。这一设计减少了重复的 SQL 模板， 也体现了 Mosaic 的核心思想——同一份数据可以支撑多种分析视角。

所有数据均为确定性合成，使用 sin、cos、% 等纯函数组合生成， 无需任何外部数据源。这一设计使得项目可以完全离线运行，也让像素级回归测试有了稳定的基准。

设计取舍

为什么用 DuckDB-WASM 而不是直接数组？因为可视化的数据量达到几十万到上百万行， 如果全部加载到 JavaScript 主线程再用 D3 之类的库渲染，会有严重的性能问题。 数据库驱动的方式让聚合在 Worker 内完成，主线程只接收屏幕分辨率级别的结果，交互更流畅。

为什么是透明 PNG 而不是嵌入页面的 SVG？透明 PNG 可以直接用于幻灯片、文档、设计稿等多种媒介， 不需要考虑样式隔离或字体差异。omitBackground: true 使得图像可以叠加在任意背景上。

为什么用像素分析而不是快照对比？像素比对（snapshot diff）对渲染细节过于敏感， 字体渲染、抗锯齿的微小差异都会导致误报。而「透明区 + 墨迹量 + 饱和度」的三项指标是结构级别的， 既能捕获实质性错误（空白图、全黑图、无颜色），又对无害的渲染波动有鲁棒性。
